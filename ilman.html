Holding Locks During Long Operations

❌ Problem

syncTenants() is called while holding a mutex lock — if it takes long, Stop() will block waiting for the lock. 

func (w *TenantSyncWorker) Start() {
    w.mu.Lock()
    defer w.mu.Unlock()

    if w.running {
        return
    }

    // ❌ Long-running call inside lock
    w.syncTenants()

    w.running = true
}

Why it’s bad: Locks should protect short critical sections only — not long network or DB calls.

✅ Fix

func (w *TenantSyncWorker) Start() {
    w.mu.Lock()
    if w.running {
        w.mu.Unlock()
        return
    }
    w.running = true
    w.mu.Unlock()

    // ✅ Run outside the lock
    w.syncTenants()
}

No Goroutine Lifecycle Management

❌ Problem

The goroutine runs indefinitely; there’s no way to track or wait for it.

func (w *TenantSyncWorker) Start() {
    go func() {
        for {
            select {
            case <-w.ticker.C:
                w.syncTenants()
            case <-w.done:
                return
            }
        }
    }()
}

Why it’s bad: Goroutines might outlive the app. Stop() doesn’t ensure it has exited. Can cause DB or HTTP connection leaks.

✅ Fix

type TenantSyncWorker struct {
    ctx    context.Context
    cancel context.CancelFunc
    wg     sync.WaitGroup
}

func (w *TenantSyncWorker) Start() {
    w.ctx, w.cancel = context.WithCancel(context.Background())
    w.wg.Add(1)

    go func() {
        defer w.wg.Done()
        for {
            select {
            case <-w.ticker.C:
                w.syncTenants(w.ctx)
            case <-w.ctx.Done():
                return
            }
        }
    }()
}

func (w *TenantSyncWorker) Stop() {
    if w.cancel != nil {
        w.cancel()
    }
    w.wg.Wait() // ✅ Wait for worker to finish
}

Slice Preallocation

❌ Problem

func convertAdminUsers(adminUsers []AdminUserFromAS) []domain.AdminUser {
    var domainUsers []domain.AdminUser
    for _, u := range adminUsers {
        domainUsers = append(domainUsers, convert(u))
    }
    return domainUsers
}

Why it’s bad: Appending to a nil slice without capacity causes multiple reallocations when len(adminUsers) is large. Each reallocation copies the slice contents → unnecessary CPU and memory churn.

✅ Fix

func convertAdminUsers(adminUsers []AdminUserFromAS) []domain.AdminUser {
    domainUsers := make([]domain.AdminUser, 0, len(adminUsers)) // ✅ preallocate

    for _, u := range adminUsers {
        domainUsers = append(domainUsers, convert(u))
    }
    return domainUsers
}

Rule of Thumb: Whenever you know or can estimate final slice size, use make([]T, 0, n).

Goroutines, WaitGroups & conc.WaitGroup

  • Goroutine — A lightweight thread in Go that runs concurrently.
  • WaitGroup — A synchronization primitive that lets you wait until a set of goroutines has finished. Each goroutine calls Done() when finished. The main thread calls Wait() to block until all goroutines are done.
  • conc.WaitGroup — A safer, cleaner replacement for sync.WaitGroup. It tracks goroutines, catches panics, and simplifies concurrency management.

💡 Tip: Prefer conc.WaitGroup over sync.WaitGroup for goroutine management in production Go code.

Lifecycle: Start / Stop with Context

A common pattern for managing background goroutines:

  1. Store the context cancel function when Start() is called.
  2. Call cancel in Stop().
  3. Wait for goroutines to exit using s.waitGroup.Wait().

This guarantees that goroutines exit cleanly when the worker is stopped.

Why Prefer Ticker Over time.Sleep

❌ Drawback of time.Sleep(30 * time.Second)

If ctx is canceled during the sleep, the goroutine cannot react immediately.

✅ Fix — Use Ticker

With a Ticker, your loop can immediately stop if ctx.Done() is triggered — no need to “wait out” the sleep duration. Using a Ticker allows you to wait for either the next tick or context cancellation, making it more responsive.

Comparing Slices as Sets — Avoid Sorting

❌ Problem

Original implementation sorted both claim slices before comparing them. 

cmClaims := append([]string{}, cm.Claims...)
otherClaims := append([]string{}, other.Claims...)

sort.Strings(cmClaims)
sort.Strings(otherClaims)

This works, but:

  • Requires sorting (O(n log n))
  • Mutates copied slices unnecessarily
  • Doesn't clearly express the intent that claims are treated as a set

PR feedback: If claims are assumed to be unique, use a map instead.

✅ Fix — Use a Map (Set Comparison)

This version:

  • Does not require sorting
  • Works regardless of order
  • Runs in O(n)
  • Clearly expresses “set equality”
  • Matches domain assumption (claims are unique)
func (cm *ClaimsMapper) Compare(actual interface{}) error {
    other, ok := actual.(*ClaimsMapper)
    if !ok {
        return fmt.Errorf("expected *ClaimsMapper, got %T", actual)
    }

    if cm.TokenProfile != other.TokenProfile {
        return fmt.Errorf(
            "claims mapper token profile mismatch: expected %s, got %s",
            cm.TokenProfile, other.TokenProfile,
        )
    }

    // Fast-fail if lengths differ
    if len(cm.Claims) != len(other.Claims) {
        return fmt.Errorf(
            "claims mapper claims count mismatch: expected %d, got %d",
            len(cm.Claims), len(other.Claims),
        )
    }

    // Build lookup map (set)
    expected := make(map[string]struct{}, len(cm.Claims))
    for _, claim := range cm.Claims {
        expected[claim] = struct{}{}
    }

    // Verify each claim exists
    for _, claim := range other.Claims {
        if _, ok := expected[claim]; !ok {
            return fmt.Errorf("claims mapper missing claim: %s", claim)
        }
    }

    return nil
}

💡 Insight: When order does not matter and values are unique, think “set comparison”, not “slice comparison”.

Run a Specific Test with Coverage (Console Output)

If you run the command from:

  • Run tests in the cmd/user-management package

MongoDB NoSuchTransaction Error in processReconciliation

❌ Error

failed to save aggregate: (NoSuchTransaction) Transaction with { txnNumber: 1 } has been aborted.

🔎 Root Cause

The NoSuchTransaction error occurs because MongoDB transactions have a default timeout of 60 seconds. Your original code was running everything inside a single rs.ts.Run() transaction while making multiple external HTTP calls to Curity. These HTTP calls can take significant time, and when the cumulative time exceeds the transaction timeout, MongoDB aborts the transaction.

✅ Fix

Restructure the code to use short-lived transactions that only perform database operations, while external HTTP calls happen outside the transactions:

  • Phase 1: Load tenant and get reconciliation data in a short transaction, then save immediately.
  • Phase 2: For each IDP, make the external HTTP call outside the transaction, then update status in a separate short transaction.
  • Phase 3: Reset database clients – external calls outside transaction, then save in a short transaction.
  • Phase 4: For each application client, external call outside transaction, then update status in a short transaction.

Summary: External HTTP calls must happen outside the transaction to avoid MongoDB timeouts.

Additional Notes: Optimistic Locking & Reloading Tenant

Load the tenant once at the beginning and reuse it for all external HTTP calls. Reload the tenant only when saving, because:

  • The aggregate pattern uses optimistic locking (version checks).
  • We need the latest version to save successfully.
  • Saving a stale tenant object would cause a version conflict.

Example of reload on save:

err = rs.ts.Run(ctx, func(ctx context.Context, repo core.Repository) error {
    t := &domain.Tenant{}
    if loadErr := repo.Load(ctx, tenantId, t); loadErr != nil {  // Get latest version
        return loadErr
    }
    // ... modify t ...
    return repo.Save(ctx, t)  // Save with correct version
})

External HTTP calls (to Curity) only need to read tenant data – they don't care about the version. Database save operations must reload the tenant to ensure the correct version for optimistic locking.

Concurrent SCIM Create User: Conflict on SCIM Source Aggregate

❌ Problem

The SCIM Create User endpoint is triggered when users are provisioned via SCIM (e.g., from Entra ID). When two concurrent create-user requests arrive simultaneously, a Concurrent Access Error occurs because both requests attempt to update the same field (userLastSync) in the same SCIM Source aggregate. Since the aggregate is versioned, concurrent updates result in a version conflict.

🔍 Root Cause

The SCIM Source aggregate uses optimistic locking. Updating userLastSync inside the aggregate on every create-user call means parallel requests race to increment the same version, and one always loses.

Attempted Solutions & Why They Fall Short

1. Mutex (In-Memory Lock)

Introduce a per-SCIM-source mutex so only one request executes at a time; other requests wait and retry. Different SCIM sources still process in parallel.

Problem: Works only in a single-pod deployment. In a multi-pod setup each pod has its own memory, so the mutex is ineffective across pods.

2. Distributed Locking (MongoDB-based)

Use a distributed lock (e.g., via core.LockManager) to allow only one request to update the SCIM Source at a time across all pods.

Problem: Becomes a bottleneck — effectively forces SCIM provisioning to run sequentially across the entire fleet, reducing scalability and throughput.

3. Partial Update Outside Aggregate (Non-versioned $set)

Stop updating the SCIM Source aggregate inside the transaction; update userLastSync separately using a non-versioned MongoDB $set.

Problem: Breaks aggregate consistency rules. An aggregate must be treated as a single unit of data; partial updates outside it violate domain design principles.

✅ Final Solution

Do not update the SCIM Source aggregate at all. Instead:

  • Store the sync timestamp (userLastSync) in the User aggregate.
  • Each user record maintains its own sync timestamp — no shared mutable state, no version conflicts.
  • To derive userLastSync per SCIM Source: query users by scimSourceId and compute the latest sync timestamp from those users.

Tell, Don’t Ask Principle (DDD / OOP)

Tell, Don’t Ask is an object-oriented design principle that says:

Instead of asking an object for its internal state and making decisions outside it… Tell the object what to do and let it decide internally.

❌ What You’re Doing (Asking)

The service pulls data out of the aggregate and makes business decisions externally: 

if !scimSourceState.AllowProvisioning {
    return fmt.Errorf("...")
}

expTime := scimSourceState.Expiry.Time
currentTime := s.clock.NowUTC().Time

if expTime.IsZero() || expTime.Before(currentTime) {
    return fmt.Errorf("...")
}

Why this violates Tell, Don’t Ask:

  • You ask the aggregate for its internal data.
  • You implement business rules in the service layer.
  • Business logic becomes scattered.
  • Aggregate invariants are not enforced by the aggregate itself.

✅ Correct Approach (Tell)

Move business rules into the aggregate and expose behavior instead of fields.

Inside the Aggregate:

func (s State) CanProvision(now core.Timestamp) error {
    if !s.AllowProvisioning {
        return errors.New("provisioning disabled")
    }

    if s.Expiry.IsZero() || s.Expiry.Before(now) {
        return fmt.Errorf("SCIM source expired on %s", s.Expiry)
    }

    return nil
}

Inside the Service (Tell the Aggregate):

if err := scimSourceState.CanProvision(s.clock.NowUTC()); err != nil {
    return fmt.Errorf("[%s] %w", logPrefix, err)
}

Now:

  • The service tells the aggregate: “Check if provisioning is allowed.”
  • The aggregate enforces its own invariants.
  • Business rules remain inside the domain.
  • The code becomes cleaner and more maintainable.

💡 Key Insight: Aggregates should protect their invariants. Services orchestrate — they should not enforce domain rules.

Test-Driven Development (TDD)

TDD stands for Test-Driven Development. It's a software development approach where you write tests before writing the actual code. It's widely used in agile and clean code practices.

💡 When doing TDD, don't test implementation details — instead, test the behaviours.

The Trigger to Writing a Test

  2. Green: Implement just enough code to make the test pass.
  3. Refactor: Improve the code (cleaner, more efficient) without changing behavior, ensuring tests still pass.

  • Writing tests first makes you think about behaviour from a user's perspective.
  • Tests give you the confidence to change code without breaking functionality.

Event Storming

Event Storming is about exploring the domain and visualizing flows of events, commands, and actors.

Core Concepts

  • Event — Represents business facts (something that already happened).
    Example: OrderPlaced, PaymentConfirmed.
  • Command — Instruction to perform an action — if successful, it results in one or more events.
    Example: PlaceOrder, CancelOrder.
  • Policy — Automatic reaction to a domain event that may issue a new command (business rule/logic).
    Example: After PaymentFailed, a policy may issue NotifyUser.
  • Aggregate — A domain object.
    Example: Order, Cart.
  • User Role — Actor (person or system) that initiates commands, which may eventually cause events.
    Example: Customer, Admin, InventoryService.
  • Process — Listens to an event and decides to issue a new command — orchestrating multi-step workflows.
    Example: After OrderPlaced, the process triggers ReserveInventory.
  • View — UI for displaying event data. Often part of CQRS.
    Example: OrderSummary UI, UserProfile UI.
  • Hot Spot — Highlights uncertainties, conflicts, or missing info that need to be clarified during modeling.
    Example: "Who owns payment retry logic?"

CQRS — Command Query Responsibility Segregation

CQRS stands for Command Query Responsibility Segregation. It's an architectural pattern used in software design that separates how you read data (queries) from how you write/update data (commands).

CQRS = separate models for writing (commands) and reading (queries), making systems more scalable, maintainable, and performant.

Hexagonal Architecture (Ports & Adapters)

Hexagonal Architecture (also called Ports and Adapters) is a software architecture pattern about structuring an application so that the core business logic (the "domain") is independent of external technologies like databases, UIs, messaging systems, or APIs.

Concepts

  • Domain — Contains business rules, use cases, and domain models.
  • Ports — Interfaces that define how the domain layer interacts with the outside world.
  • Adapters — Implementations of those ports for specific technologies.

Example: E-commerce Order Service

  • Domain: OrderService with method placeOrder() (business rules).
  • Inbound Port + Adapter:
    • Port: OrderUseCase interface.
    • Adapter: REST controller that translates HTTP request into a placeOrder() call.
  • Outbound Port + Adapter:
    • Port: OrderRepository interface / PaymentGatewayPort
    • Adapter: PostgresOrderRepository or MongoOrderRepository / StripePaymentAdapter or PaypalPaymentAdapter

The business logic doesn't care whether persistence is Postgres or Mongo, or whether payments are via Stripe or PayPal — it just calls the port.

Comparison with Other Architectures

1. Layered Architecture (a.k.a. n-tier)

  • Organizes code in horizontal layers (common in Java/Spring apps).
  • Rules: upper layers can call lower layers, but not the other way around.
  • Cons: business logic can leak into controllers or repositories, so it would be hard to test in isolation.

2. Hexagonal Architecture

  • The domain (serviceImpl) is located at the center, surrounded by ports (interfaces) and adapters (implementations), so the system is independent of frameworks, UIs, or databases.
  • Pros: Testable.
  • Cons: More boilerplate code and similar interfaces.

3. Clean Architecture

  • An evolution of hexagonal — emphasizes dependency rules where inner circles know nothing about outer circles.

Idempotent Operations

Definition: An operation is idempotent if calling it multiple times gives the same result.

Example: If an endpoint updates a field (active) in an existing resource (user), use PUT.
It is idempotent — calling it multiple times doesn’t change the result.

Why PUT Fits Update-Existing-Field Endpoints

If an endpoint's purpose is to update an existing field (e.g., active) in an existing resource (e.g., user):

  • PUT is used to update or replace an existing resource or a specific field of it.
  • You already know the user's {id} — so it's not a creation, which would use POST.
  • The operation is idempotent — calling it multiple times gives the same result (activating the user again doesn't change anything).

HTTP Redirect Codes

  • 302 Found: This status code indicates that the requested resource is temporarily located at a different URI. The key aspect of a 302 redirect, according to the HTTP specification, is that the client is supposed to repeat the request to the new URI using the same HTTP method as the original request. For example, if a POST request results in a 302, the browser should theoretically issue another POST request to the new location. However, in practice, many browsers and clients historically treated 302s as if they were 303s, changing the subsequent request method to GET, especially after a POST.
  • 303 See Other: This status code explicitly instructs the client to retrieve the redirected resource using a GET request, regardless of the original request's method. It is commonly used after a successful POST, PUT, or DELETE operation where the server wants to redirect the client to a different resource (e.g., a confirmation page or the newly created resource) to prevent resubmission issues and allow for bookmarking of the result.

  • Snapshots

Application
   ↓ (plain BSON)

   ↓

Scanning Container Images with Trivy

Trivy is an open-source vulnerability scanner from Aqua Security. It inspects container images (and other targets like filesystems, Git repos, and Kubernetes manifests) and reports known security issues — typically CVEs in OS packages and application dependencies bundled inside the image.

Why use Trivy?

  • Catch known vulnerabilities before deployment. A clean build does not mean a safe image — base images and installed packages may carry published CVEs.
  • Shift-left security. Run it locally or in CI after docker build and before pushing to a registry, so bad images are blocked early.
  • Registry-ready images. Many teams require a Trivy scan (with severity gates) before an image is promoted to staging or production.
  • Fast, no agent required. Trivy runs as a standalone CLI or container — useful on a laptop, in CI, or as a one-off check against an image already in ACR.

Trivy does not replace runtime protection, secret scanning, or code review. It answers one specific question: "Does this image contain known vulnerabilities in its OS packages or dependencies?"

Scan an image from ACR

This runs Trivy in a throwaway Docker container. Mounting /var/run/docker.sock lets Trivy use the local Docker daemon to pull and inspect the target image (or use an image already present locally). 

docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest \
  image <ACR_NAME>.azurecr.io/<IMAGE_PATH>:<TAG> \
  --severity MEDIUM,HIGH,CRITICAL \
  --ignore-unfixed \
  --format table

Example (Curity IAM image):

docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest \
  image nxsdvlglb01acr.azurecr.io/nexus/iam:11.1.1 \
  --severity MEDIUM,HIGH,CRITICAL \
  --ignore-unfixed \
  --format table

Flag breakdown

Flag / option What it does
docker run --rm Run Trivy once and remove the container when finished.
-v /var/run/docker.sock:... Gives Trivy access to the host Docker daemon so it can pull/inspect images.
image <ref> Trivy subcommand: scan a container image (by tag or digest).
--severity MEDIUM,HIGH,CRITICAL Only report vulnerabilities at these severity levels — skips LOW and UNKNOWN noise.
--ignore-unfixed Hide CVEs that have no upstream fix yet — focuses on issues you can actually patch.
--format table Human-readable table output (alternatives: json, sarif for CI).

Typical workflow: build image → run Trivy → fail CI if CRITICAL/HIGH findings remain → push to ACR only when the scan passes (or when exceptions are documented). Log in to ACR first if the image is private: az acr login --name <ACR_NAME>.

Curity Probe Tuning Under Heavy Config Load

❌ Symptoms

TimeoutException / ConnectException / ConfException: unexpected end of file / EOFException / CdbListener - Exception when handling subscription triggers in logs of runtime pod, and the runtime pod goes to Not Ready state.

🔎 Why?

This strongly suggests the admin node wasn't accepting cluster connections from runtime nodes (or was too slow to complete mutex/topology work) during a large config apply. As a result, the runtime nodes can't register themselves with the admin node on port 6790. The readiness probes then fail, and the pod goes to Not Ready.

✅ Solution — Increase timeoutSeconds and periodSeconds

  • Why increase timeoutSeconds to 30s? While the admin is applying a huge config (or the runtime is recovering), the JVM can be slow: long GC pauses, threads busy on cluster/config work, etc. The health handler may still be fine but not answer within 10s.
  • Why increase periodSeconds to 30s? This sends less probe traffic to the admin node, giving fewer chances per minute to hit a "slow window" and stack up failures. 
--set curity.admin.livenessProbe.initialDelaySeconds=180 \
--set curity.admin.livenessProbe.timeoutSeconds=30 \
--set curity.admin.livenessProbe.periodSeconds=30 \
--set curity.admin.livenessProbe.failureThreshold=10 \
--set curity.admin.readinessProbe.initialDelaySeconds=120 \
--set curity.admin.readinessProbe.timeoutSeconds=30 \
--set curity.admin.readinessProbe.periodSeconds=30 \
--set curity.admin.readinessProbe.failureThreshold=10 \
\
--set curity.runtime.livenessProbe.initialDelaySeconds=180 \
--set curity.runtime.livenessProbe.timeoutSeconds=30 \
--set curity.runtime.livenessProbe.periodSeconds=30 \
--set curity.runtime.livenessProbe.failureThreshold=10 \
--set curity.runtime.readinessProbe.initialDelaySeconds=120 \
--set curity.runtime.readinessProbe.timeoutSeconds=30 \
--set curity.runtime.readinessProbe.periodSeconds=30 \
--set curity.runtime.readinessProbe.failureThreshold=10

Short Causal Story

  • Large config on admin makes the admin and/or cluster path slow or briefly unavailable (6790).
  • As a result, runtime loses or struggles with its cluster connection to admin.
  • During the same window, the runtime JVM is busy or paused, so the readiness probe sometimes doesn't finish in time, which makes Kubernetes mark the pod as NotReady.

The runtime doesn't go NotReady because Kubernetes understands "disconnected from admin"; it goes NotReady because the probe fails, and that often happens at the same time as the cluster disconnect due to load, timeouts, and admin instability.

How to Prevent This Situation

  • Use longer / less aggressive readiness on runtime (and liveness on admin) so slow health during load doesn't flip NotReady / restart admin.
  • Allocate more admin resources, so 6790 and config apply finish faster — fewer disconnects and less runtime churn.

Managed Identity (Azure)

A Managed Identity is an Azure AD identity automatically managed by Azure. It removes the need for you to manually create and rotate credentials.

  • System-assigned: An identity that’s tied to one resource (e.g., an AKS pod or VM). It’s deleted automatically when the resource is deleted.
  • User-assigned: A reusable identity created as a standalone resource. Multiple resources (e.g., AKS pods, Functions, etc.) can share it.

Steps to Configure Managed Identity for AKS

  1. Enable Workload Identity: 
    az aks update \
  --name <aks-cluster-name> \
  --resource-group <resource-group> \
  --enable-oidc-issuer \
  --enable-workload-identity

    This sets up the OIDC issuer URL so pods can use federated tokens. A federated token is a Kubernetes service account token that Azure AD accepts (through federation) to issue an Azure access token.

  2. Create User-Assigned Managed Identity: 
    az identity create \
  --name my-app-identity \
  --resource-group <resource-group>

    Then note the clientId and resourceId from the output.

  3. Give Key Vault Access to this identity:

    Get the vault name and identity client ID, then:

    az keyvault set-policy \
  --name <keyvault-name> \
  --secret-permissions get list \
  --spn <clientId-of-identity>
  4. Federate the Managed Identity with your AKS OIDC Issuer:

    Get your AKS OIDC issuer URL:

    az aks show \
  --name  \
  --resource-group  \
  --query "oidcIssuerProfile.issuerUrl" \
  -o tsv

    Then create a federated credential for your app’s service account:

    az identity federated-credential create \
  --name my-app-federation \
  --identity-name my-app-identity \
  --resource-group <resource-group> \
  --issuer <aks-oidc-issuer-url> \
  --subject system:serviceaccount:<namespace>:<serviceaccount-name>

Cookie Overwrite Problem & Fix

The Problem:

Curity tracks an interactive authentication transaction server-side and links it to the browser by a session cookie (sessionid + ssm). When you start login with lec-oidc (customer profile), Curity creates a session (call it session A) and stores the OIDC state there.

In your flow lec-oidc delegates to lec-token-profile → azure-oidc → Entra ID. During that delegation, the lec-token-profile (or azure-oidc running under it) also performs top-level redirects and may itself write a new session cookie (call it session B) under the same cookie name and same domain.

Because both profiles are served from the same domain and the session cookies use that domain and a non-restrictive path, the browser accepts and stores the latest Set-Cookie value — which can overwrite the original session cookie value (session A → replaced by session B).

When the IdP redirects the browser back to customer callback with code+state, the browser sends the current cookie value (session B). Curity's customer profile then looks up session B server-side and finds either the wrong session or no authn transaction (or the state does not match). Result: "Couldn't resume authentication transaction / missing_parameters".

The Solution:

  • Serve profiles on different hostnames (or subdomains)
    • Put the lec-token-profile / lec-authentication-profile and the customer profile on separate hostnames (or subdomains). Example:
      • lec-token-profile → https://lec.rgn-eu.nxs-dev.ifscsc.cloud
      • customer profile → https://app.rgn-eu.nxs-dev.ifscsc.cloud
    • Because cookies are scoped per host, session cookies from lec.example.com will not overwrite cookies on app.example.com. This is the cleanest and safest fix.
    • Implementation: change the base URLs / virtual host mapping (ngrok endpoints / DNS) used for each profile so they use different hostnames.

PS: If you serve the lec-token/lec-authentication profiles from lec.rgn-eu.nxs-dev.ifscsc.cloud while the customer profile stays on rgn-eu.nxs-dev.ifscsc.cloud, the browser will keep separate cookie namespaces for the two hosts and the lec profile will not overwrite the customer session cookie.

How to apply the fix:

  1. Pick distinct hostnames for the profiles. Example:
    • app.rgn-eu.nxs-dev.ifscsc.cloud (customer-facing profile)
    • lec.rgn-eu.nxs-dev.ifscsc.cloud (lec-token / IdP profile)
  2. Find the address your DNS should point to (Ingress / Load Balancer). Determine how external traffic reaches your cluster (Ingress controller service). Run: 
    kubectl get svc -n kube-system
kubectl get svc -n <ingress-namespace>

    Look for the Service that fronts Traefik/Nginx (type LoadBalancer) and note either:

    • EXTERNAL-IP (an IP)
    • EXTERNAL-DNS NAME (an ELB/ALB DNS name)
  3. Create DNS records in your provider:
    • EXTERNAL-IP 34.12.45.67 → create A records pointing to that IP
    • EXTERNAL-DNS curity-alb-123456.us-east-1.elb.amazonaws.com → create an ALIAS (Route53) or CNAME pointing to that DNS name
  4. Create/adjust Ingress YAML to accept both hostnames and route to your Curity service.
  5. Update Curity profile base-urls and client redirect_uris to the new hostnames.
    • For the lec-token/lec-authentication profiles: update base-url (if used in discovery) and client redirect_uris and configuration-urls to use lec.rgn-eu...
    • For the customer profile (customer-test): update the lec-oidc authenticator configuration-url and any clients’ redirect_uris that point to the callback to use app.rgn-eu...
  6. Test with browser and verify cookies are not overwritten.

What Is Authentication?

Authentication means verifying the identity of a caller based on credentials. The credential could be:

  • Username + Password
  • Client ID + Client Secret
  • API key
  • Session cookie
  • Access token
  • Certificate

1. Username + Password

The client sends a username and password; the server verifies the password. At the moment the server verifies the password, authentication has occurred.

The server may then create a session cookie, issue a JWT, return an access token, or do nothing further — authentication happened regardless.

2. Secret (Password, Client Secret, or API Key)

A secret is a credential used to authenticate a client or user. The server stores a hashed version; the client presents the plain secret to prove identity. 

Authorization: Bearer my-secret-value
# or
x-api-key: my-secret-value

The API receives the secret, hashes it, compares with the stored hash, and if they match the caller is authenticated — because the caller has proved possession of a valid credential.

Authorization with secrets — two cases:

  • Case A: Single secret for the entire API
    You have one stored secret hash and nothing else. A valid secret grants all permissions. Common in simple SCIM implementations.
  • Case B: Multiple secrets / clients
    Each secret maps to a permission set (e.g., read-only, read+write, admin). After authenticating the secret, you look up the associated permissions and perform authorization checks.

3. Access Token

A token is a credential that represents an authenticated identity and may also carry authorization information. Tokens are issued after successful authentication and typically have an expiration time. 

Authorization: Bearer eyJ...

Before the token was issued, the client authenticated to Curity, Curity validated the credentials, and Curity issued the token.

When your API receives the token, it validates: signature (JWT) or introspection (opaque token), issuer, audience, and expiration. If valid, the API accepts the caller’s identity — that acceptance is also authentication.

After authenticating the token, you perform authorization based on the scope claim (e.g., scope must contain scim.read).

Is token validation authentication? Yes. The API authenticates the caller by validating an access token issued by a trusted authority (Curity). You are not authenticating the client directly, but you are authenticating its token.

Federation Concepts

Federation = One system trusting another system’s users or identities (tokens).

  • User Federation: Connect IdP to external datasource so that users can authenticate using accounts that are managed outside your system.
  • OIDC Federation: One OIDC provider trusts tokens from another. This is usually done by setting the issuer URL of one IdP in the other IdP.
  • Federated Token: A token issued by the trusted external system (AKS) that Azure AD will accept because of OIDC federation.
  • Federated Credential: It’s a rule that we configure in Azure AD in order to enable it to accept federated tokens.

IdP (Identity Provider)

  • An Identity Provider (IdP) is a system that authenticates users
  • An External IdP is an outside IdP that your system trusts to authenticate users instead of doing it itself.
  • In your setup:
    • Your Curity server is the main IdP for your apps.
    • But, Curity delegates login to Azure AD, which acts as the external IdP.

Identity Provider vs Authorization Server

In OAuth2 and OpenID Connect, the terms Identity Provider (IdP) and Authorization Server are closely related but have distinct roles:

  • Identity Provider (IdP) — focuses on authenticating the user. Handles login (e.g., obtaining an authorization code by passing credentials to an external IdP).
  • Authorization Server — focuses on issuing tokens. Handles exchanging the authorization code for an access token, or issuing tokens for client credentials.

Curity acts as both: it authenticates the user (IdP) and issues tokens based on scopes and grant types (Authorization Server).

  • IdP → authentication (who you are)
  • Authorization Server → authorization (what you can do)

OpenID Connect (OIDC) — The Protocol

  • OpenID Connect (OIDC) is a protocol that is used to authenticate users.
  • It is used by OIDC providers — in other words, OIDC providers implement the OIDC protocol.
  • Example of an OIDC provider in Curity: the OIDC Authenticator.

One OIDC provider delegating authentication to an external OIDC provider — and trusting the tokens issued by that external OIDC provider — is called an OIDC federation.

What is an OpenID Connect (OIDC) provider?

  • An OpenID Connect (OIDC) provider is a service that authenticates users and issues tokens
  • Examples: Curity, Azure AD (Entra ID), Google, Okta.
  • In your setup: Customer profile, LEC profile or Azure AD acts as the OIDC provider.

What is an OIDC federation?

  • An OIDC federation is when multiple OpenID Connect (OIDC) providers (or realms/identity systems) are connected or trusted together, so users from one system can authenticate in another.
  • In your setup: Your customer profile acts as an OIDC provider. This OIDC provider delegates login to another OIDC provider — e.g., LEC profile or Entra ID (Azure AD). This setup forms an OIDC federation, where customer profile acts as a relying party to another OIDC provider.

IdP vs OIDC

  • IdP authenticates users. It can use different protocols to do authenticaion, such as
    • OIDC (OpenID Connect)
    • SAML
  • In your setup:
    • Curity contains a tenant profile that issues tokens. Therefore, curity acts as an IdP.
      But Curity is delegating authentication to another IdP — Azure AD (Entra ID) — through OIDC. Therefore, Azure AD is an extrenal IdP.
    • Your app uses OIDC to talk to Curity (that’s how it gets tokens).
      Curity uses OIDC again, but this time as a client to Azure AD (external IdP).

OAuth 2.0 & OpenID

  • How to Say You’re Using OAuth 2.0?
    • Your flow includes /oauth/authorize and /oauth/token endpoints.
    • You exchange an authorization code for an access token.
    • The purpose is to obtain a token to call APIs (authorization).
  • How to Say You’re Using OpenID Connect?
    • The scope parameter includes openid.
    • You receive an ID Token (usually a JWT with user claims).
    • You have an OIDC discovery document endpoint (/.well-known/openid-configuration).
    • You use authenticators or clients of type oidc.
    • The goal is user authentication (not just API access).
  • OpenID Connect (OIDC) is built on top of OAuth 2.0 — it extends OAuth2.
  • In your setup:
    • Between your application ↔ Curity: using OAuth 2.0 (authorization) — and OIDC if scope=openid is included for login.
    • Between Curity ↔ Azure AD: using OpenID Connect, which internally uses OAuth 2.0 flows.

Authentication in OAuth

Authentication in OAuth depends on the grant type being used.

Authorization Code Flow

Both the user and the client are involved:

  • The user authenticates (e.g., username/password, MFA, passkey).
  • The client identifies itself (using PKCE and optionally a client secret).
  • The authorization server issues tokens.

The resulting access token represents: the authenticated user acting through the authenticated client.

Client Credentials Flow

No user is involved:

  • The client application authenticates itself using a client secret, private key, or certificate.
  • The authorization server issues a token.

The resulting access token represents: the authenticated client application itself.

Purpose of Scopes When Obtaining a Token

In OAuth2, a scope defines the level of access a client is requesting. Scopes are sent in the /oauth-token request (e.g., scope=openid email scim.read) and must be recognized and allowed for the client.

  • openid — triggers OpenID Connect behavior; an ID token is issued. The ID token contains user identity information (sub, iss, aud, etc.), is used by the client to verify the authenticated user, and can be passed as id_token_hint in logout requests to identify which session to terminate.
  • profile — includes profile-related claims (e.g., name, preferred_username). Claims are configured and linked to the profile scope in the IdP; they are only included in the token when this scope is requested.
  • Custom scopes (e.g., scim.read) — represent API-level permissions. Included in the scope claim of the access token and used by APIs to authorize actions (e.g., read SCIM users/groups).

When no scope is provided: the server may apply default scopes or issue a limited token, depending on configuration.

What is SCIM?

SCIM = System for Cross-domain Identity Management. A protocol to sync users between systems.

Push-Based Provisioning

SCIM is push-based provisioning. When a user:

  • Is created
  • Is updated
  • Is disabled
  • Is removed from a group

…Entra automatically calls the application's SCIM endpoint.

Identity Authority

The External IdP becomes the identity authority — i.e., the External IdP is considered the source of truth for user identity data.

Example flow:

  • User leaves the company → disabled in Entra.
  • SCIM sets active=false.
  • User can no longer log in.

💡 So in this setup: Entra is the identity authority, Curity is the identity broker.

Why is a SCIM Secret Called a “Bearer Token”?

In SCIM, the term “Bearer token” refers to how the value is sent in the HTTP request (via the Authorization: Bearer <value> header), not necessarily what the value actually is. In systems like Entra SCIM provisioning, the value itself is typically a long-lived, static credential — meaning it behaves like a secret (similar to an API key).

However, because it is transmitted using the Bearer token convention, it is referred to as a “token.” So in practice, it is a secret that is simply carried using the Bearer token format.

SCIM API Authentication with Entra Provisioning — Q&A

Q: What is the best approach for SCIM API authentication with Entra provisioning?

The best approach is to use OAuth 2.0 Client Credentials with Curity rather than long-lived static bearer secrets validated directly by the application.

Entra ID obtains a short-lived access token from Curity using the client_credentials grant and sends that token to the SCIM API. The SCIM API validates the token instead of a permanent shared secret.

Q: What is the problem with using a static secret directly as the bearer token?

A static bearer secret works technically, but has several security and architectural limitations:

  • The secret is usually long-lived or non-expiring.
  • If leaked, an attacker can provision/deprovision users and call SCIM APIs until the secret is rotated.
  • No proper token lifecycle management.
  • Cannot easily perform authorization using scopes.
  • Harder to support revocation, rotation, client isolation, and auditability.
  • Not the industry-standard model for enterprise integrations.

This approach essentially treats the bearer token as an API key / shared secret.

Q: When would using a static secret directly as the bearer token or an API key be acceptable?

A static secret may be acceptable in simpler environments such as:

  • Internal-only systems (e.g., no public ingress, VPN-protected)
  • Isolated networks (e.g., tight firewall rules)

Q: Why is OAuth 2.0 Client Credentials with Curity better?

  • Access tokens are short-lived — even if stolen, the impact window is limited.
  • The API can perform authorization using scopes such as scim.read / scim.write.
  • Follows the industry-standard OAuth2 model.
  • Easier secret rotation and operational management.
  • Better auditing and monitoring.
  • Cleaner separation of responsibilities: Curity handles authentication and token issuance; the SCIM API handles authorization and business logic.

Q: In OAuth2 client_credentials, isn’t the client secret still long-lived?

Yes — the client secret itself is still long-lived. However, the key difference is that the client secret is used only to obtain short-lived access tokens and is never sent to the SCIM API directly. 

# Static secret approach (avoid)
Authorization: Bearer <permanent-secret>

# OAuth2 client_credentials approach (recommended)
Entra → Curity → obtain short-lived access token
Authorization: Bearer <short-lived-access-token>

Even if the access token is leaked, it expires quickly.

Q: What is the recommended architecture?

Entra ID SCIM Provisioning
        |
client_id + client_secret
        |
Curity Token Endpoint
        |
short-lived access token
        |
SCIM API

The SCIM API validates JWT access tokens by:

  • Verifying the signature via JWKS.
  • Validating issuer, audience, expiry, and scopes.

This is the modern enterprise-grade SCIM authentication model.

OAuth2 Client Credentials vs Basic Auth for Service-to-Service Communication

Q: What is the best choice for internal K8s cluster-to-cluster communication

For internal service-to-service communication from one Kubernetes cluster to another, the best choice is usually still OAuth2 client_credentials rather than Basic Auth, because it gives:

  • Short-lived access tokens
  • Scopes / authorization
  • Industry-standard service-to-service authentication

Q: What is the problem with Basic Auth?

Basic Auth means: Authorization: Basic base64(username:password)

Problems:

  • Credentials are long-lived
  • Password is sent on every request
  • No expiry
  • Difficult rotation
  • No scopes / authorization model
  • Leaked credentials remain usable until manually changed

It behaves like a permanent shared secret.

Q: Why is OAuth2 better even inside Kubernetes?

It is tempting to think: “It’s internal traffic, so Basic Auth is enough.” But internal networks are not fully trusted anymore. In Kubernetes environments, pods can be compromised, logs may leak headers, and secrets may leak.

OAuth2 reduces blast radius because:

  • Tokens expire
  • Scopes limit permissions
  • Access can be revoked centrally (whether clients are allowed to obtain or use tokens)

Q: When is Basic Auth acceptable?

Basic Auth is acceptable if:

  • Internal-only system (e.g., no public ingress)
  • Temporary integration
  • No authorization requirements
  • Operational simplicity is more important than security maturity

SCIM vs Federated Login Mismatch (arc → bear)

❌ Problem

In our setup, SCIM provisioning is performed from our Entra tenant using the existing arc users, while user authentication is delegated via Entra federation to an external IdP (bear).

Although authentication happens through bear, the OIDC token consumed by Curity is still issued by our Entra tenant. However, due to federation, Entra may present the user with a different login representation (for example, preferred_username / UPN changes from @arc.com to @bear.com).

Because SCIM provisioning was not updated to reflect this change, the local database still contains the arc email, while login tokens carry the bear email. Since Curity performs a lookup based on preferred_username, this results in a mismatch and login failure.

✅ This behavior is correct and secure — Curity must not guess or heuristically match users based on mutable attributes like email.

🔎 Root Cause

The core issue is that email / UPN is being used as an identity key in a system that allows federated authentication. Once federation is enabled, email and UPN are no longer stable identifiers — they are only login hints.

Identity continuity should instead be anchored to immutable Entra-issued identifiers such as oid (preferred) or iss + sub.

✅ Recommended Fix

  • Stop using preferred_username as the primary lookup key.
  • Introduce proper account linking based on immutable Entra identifiers.
  • Allow login-time linking to reconcile SCIM-provisioned users with federated login identities.

Account Linking vs Lookup

Question: "If Curity only needs to check that the user exists and pull user info into the auth context, why bother linking accounts?"

Short answer: Lookup solves "who is this right now"; account linking solves "who is this over time and across identity sources."

  • Lookup answers: Do I know a user with this identifier?
  • Linking answers: Is this external identity permanently bound to this local user?

The Real Problem Account Linking Solves

1. Identifiers are not stable.

You rely on something like userone@abc.onmicrosoft.com, but in Entra ID this can change due to:

  • UPN changes
  • Domain migration
  • Email rename
  • Guest → Member conversion
  • Multi-tenant login
  • Alias changes

If you don't link, then tomorrow the same human logs in with a different preferred_username, and your lookup fails with "user not found". With linking, you bind Entra's immutable subject (sub, oid, iss) to your local user once.

2. Multi-IdP and future expansion.

Today, the user can log in via only one IdP (e.g., github). Tomorrow, the user should be able to log in with a new IdP (e.g., entra-id). With linking, you can have one person, many identity providers, one local account. Without linking, you are silently building a single-IdP system, where the user can log in only via one IdP

3. Auditing.

Without account linking, there is no proof of identity binding.

When is Lookup Alone Sufficient?

Lookup-only is acceptable when ALL of the following are true:

  • Single IdP — user logs in only via one IdP for a tenant.
  • Stable immutable identifier — no UPN or domain-name changes to emails in the future.
  • No future federation plans — e.g., Entra ID does not federate logins to partner Entra.
  • No security/audit requirements — no need to keep track of users whose accounts are linked to an external identity.
  • Short system lifetime.

What is gRPC?

In gRPC, a client application can directly call a method on a server application on a different machine. On the server side, the server implements an interface and runs a gRPC server to handle client calls. On the client side, the client has a stub (referred to as just a "client" in some languages) that provides the same methods as the server.

gRPC uses Protocol Buffers. This is a mechanism for serializing structured data — think of it as similar to a Jackson Serializer that serializes Java objects to JSON. Protocol Buffers serialize structured data to bytes. So a proto request and response contains bytes, unlike an HTTP request/response that contains application/json, etc.

Why Use gRPC for Internal Service-to-Service Communication?

Pure HTTP/JSON:

  • Is slower (due to JSON parsing).
  • Doesn't enforce strict types between services.
  • Doesn't support streaming well.

💡 So it is recommended to use gRPC for internal service-to-service communication.

Protocol Buffers (protobuf)

Protocol Buffers (protobuf) is a way to define structured data — like the shape of a message that two systems want to exchange.

Think of .proto files like a contract: "This is how a User, Order, or Message should look, no matter what language or system is using it."

Workflow

The first step when working with protocol buffers is to define the structure for the data you want to serialize in a .proto file: this is an ordinary text file with a .proto extension.

Once you've specified your data structures, you use the protocol buffer compiler protoc to generate data access classes in your preferred language(s) from your proto definition. These provide simple accessors for each field, like name() and set_name(), as well as methods to serialize/parse the whole structure to/from raw bytes.

Defining a gRPC Service

You define gRPC services in the same proto files, with RPC method parameters and return types specified as protocol buffer messages: 

// The greeter service definition.
service Greeter {
  // Sends a greeting
  rpc SayHello (HelloRequest) returns (HelloReply) {}
}

// The request message containing the user's name.
message HelloRequest {
  string name = 1;
}

// The response message containing the greetings.
message HelloReply {
  string message = 1;
}

🔎 Understanding the Error

grpcurl needs to understand:

  • Available services
  • RPC methods
  • Request message types
  • Response message types

There are two ways grpcurl can obtain this information:

  1. From the gRPC Reflection API exposed by the server.
  2. From local protobuf descriptors supplied by the user.

In this case, the User Management gRPC server did not expose the Reflection API. Therefore grpcurl could not discover the service definitions automatically and failed before sending the request.

What happened here:

  • Buf read all .proto files.
  • Buf compiled the protobuf definitions.
  • Buf generated a descriptor set file named user-management.protoset.

This file contains all service and message definitions required by grpcurl.

Zero Trust Principle

Zero Trust means: “Never trust anything — always verify.”

According to the zero trust principle, every request must be:

  • Authenticated — who are you? (e.g., every request must contain tokens, certificates, or use mTLS.)
  • Authorized — do you have permission? (e.g., every request must include access control checks.)
  • Verified continuously — are you still who you claim to be, and is your device secure? (e.g., tokens must be validated continuously.)

JWT Validation using JWKS

JWT validation is the process of ensuring that a token is authentic, issued by a trusted IdP / Authorization Server (e.g., Curity), and allowed to access a resource. It has two main parts: signature verification (using JWKS) and claims validation.

What is JWKS?

JWKS (JSON Web Key Set) is an endpoint exposed by the IdP that provides public keys. APIs (resource servers) use these keys to verify JWT signatures. The IdP signs tokens with a private key; the corresponding public key is shared via JWKS.

How the JWKS URL is Obtained

  • Derive from the trusted issuer (iss):
iss = https://idsvr.company.com/oauth/v2/oauth-anonymous
  → https://idsvr.company.com/oauth/v2/oauth-anonymous/.well-known/openid-configuration
  → response contains: jwks_uri

Alternatively, jwks_uri can be statically configured in the application.
⚠️ Do NOT blindly trust the iss in the token — the issuer must be pre-configured and trusted.

Validation Flow

  1. Extract JWT from the Authorization: Bearer <JWT> header.
  2. Decode JWT header (do not trust yet) — read alg and kid.
  3. Obtain JWKS — call <issuer>/.well-known/openid-configuration, read jwks_uri, fetch JWKS.
  4. Select correct key — match JWT kid with a key in JWKS.
  5. Verify signature ✅ (critical step) — use the public key matching kid and the algorithm from the token (e.g., RS256).
    This proves the token was issued by the trusted IdP and has not been modified.
    This step only proves authenticity — it does not validate expiry, audience, or permissions. Reject the token immediately if verification fails.
  6. Validate claims ✅ — check:
    • iss — must match expected IdP
    • aud — must match your API
    • exp — token must not be expired
    • nbf — token must be valid now
    • iat — optional sanity check
    • scope — must contain required permissions (e.g., scim.read)

Key Concepts

  • Signature verification ≠ full validation.
  • JWKS is used only for signature verification.
  • Claims validation enforces access control.
  • Key rotation: the IdP may rotate keys (new kid). Cache JWKS and re-fetch when a kid is not found.

✅ Summary

JWT validation ensures the token is genuine (signature verified via JWKS), valid (claims checked), and has the required permissions (scope validated). Only after full validation should the API trust and process the request.

Token Validation Flow (ValidateToken)

The ValidateToken method first parses the JWT without signature verification to read the iss (issuer) claim. This is necessary to determine which verifier to use, since the service supports multiple token sources.

Kubernetes Path

If the token's issuer matches the configured Kubernetes issuer, it verifies the token using the K8s JWKS verifier, which is created at startup using the nga-common library's JwtTokenVerifier and JwkKeySetCache.

The nga-common library handles fetching the public keys from the Kubernetes JWKS endpoint, caching them in memory, and periodically refreshing them. On success, it returns the result with IssuerTypeKubernetes and uses the tenant ID from the gRPC header (not from the token itself), since K8s service-account tokens don't carry a tenant_id claim.

IdP (Curity) Path

If the issuer is not Kubernetes and the Curity verifier is enabled, it extracts the tenant_id claim from the (still unverified) token. This tenant ID is used to look up or lazily create a tenant-specific JWKS verifier from the TenantVerifierCache, which caches verifier instances per issuer in a sync.Map.

The actual cryptographic key caching (JWKS fetching and refresh) is handled internally by the nga-common library's JwkKeySetCache. On successful verification, the tenant ID is taken from the token claim (not the header), and the result is returned with IssuerTypeIdP.

Fallback

If neither path is taken (issuer doesn't match K8s and Curity is not enabled), it returns a "no token verifier configured" error.

Auth Gateway: Single-Tenant vs Multi-Tenant Configuration

If all requests authenticate against a single OAuth client (one IdP, one client ID/secret), a single-tenant gateway is sufficient. If different tenants need to authenticate against their own OAuth clients (each with their own IdP endpoints, client IDs, secrets, and redirect URLs), a multi-tenant gateway is needed.

Both modes serve the same purpose — providing a TenantConfig (client ID, client secret, auth URL, token URL, logout URL, redirect URL, and scopes) needed for OAuth flows like authorization code exchange and token refresh. They differ in where this configuration comes from.

Single-Tenant Mode

All OAuth configuration (client ID, client secret, auth URL, token URL, logout URL, redirect URL) is provided directly via static config at startup. The SingleTenantConfigProvider simply returns these pre-configured values for every request. There is only one application and one hardcoded tenant ID ("single-tenant"). No caching layer is needed since the config is already in memory.

Multi-Tenant Mode

OAuth configuration is dynamic and per-tenant. When a request arrives, the tenant is identified by the incoming host (domain name). The CachedTenantConfigProvider first checks a local cache (backed by a TransactionScope/repository, which uses Redis). On a cache miss, it delegates to the underlying user-management gRPC client, which calls FindTenantByHost on the user-management service.

The user-management service returns the tenant's auth URL, token URL, logout URL, and a list of applications (each with their own client ID, client secret name, scopes, and redirect URL). This response is then cached so subsequent requests for the same tenant don't need the gRPC call. The cache also includes request deduplication via sync.Map + WaitGroup to prevent thundering herd when multiple concurrent requests hit a cache miss for the same tenant.

⚠️ One nuance worth noting: in multi-tenant mode, the gRPC response carries a ClientSecretName (not the secret itself), while single-tenant mode provides the ClientSecret directly in config. This suggests the actual secret resolution for multi-tenant happens elsewhere (likely from a secrets manager or Kubernetes secret).

Why the Auth Gateway is Deployed as a Sidecar

Why the auth-gateway is deployed as a sidecar — and not as a separate service or a library.

What the Auth Gateway Does (Quick Recap)

The auth-gateway:

  • Handles OAuth 2.0 login / callback / logout flows.
  • Manages user sessions in Redis.
  • Acts as a reverse proxy that injects Authorization: Bearer <token> headers into requests before forwarding them to the actual backend service.

Why NOT a Shared / Centralized Service?

  1. Single point of failure — if the centralized auth service goes down, every backend behind it becomes unreachable. With a sidecar, if one pod's auth-gateway has issues, only that pod is affected.
  2. Extra network hop + latency — every request would travel: Ingress → Auth Service → Backend. With a sidecar, the auth-gateway and the backend communicate over localhost.
  3. Tight coupling to backend lifecycle — the auth-gateway needs to be colocated with its backend because it proxies to http://localhost:8082 (the backend's HTTP port) using PROXY_ROUTES.
  4. Per-application configuration — each backend has its own PROXY_ROUTES, BYPASS_HEADERS, BYPASS_PATHS, and APPLICATION_ID.

Why NOT a Library?

  1. Language independence — the auth-gateway is written in Go, but the backends it protects could be in any language. A library would force every team to use Go or maintain ports in every language.
  2. Independent release cycle — a sidecar can be upgraded independently without recompiling or redeploying the backend application. A library upgrade requires the backend team to update the dependency, rebuild, and redeploy.

Using X-Tenant-Id Header for UM Endpoints

Question: Is using the X-Tenant-Id header for UM endpoints OK?

Answer:

The cleanest design is to always include tenant_id in the token, since it keeps tenant context consistent and avoids extra validation logic.

However, in cases where:

  • The request is made by a trusted internal service (e.g., Config Service)
  • The endpoint is not exposed to end users
  • It runs within a controlled environment (e.g., Kubernetes, mTLS, gateway)

Using an X-Tenant-Id header is an acceptable approach.

⚠️ This header should still be validated against the calling service identity from the token and never blindly trusted.

What is SSO?

SSO (Single Sign-On) is an authentication concept where a user logs in once and gains access to multiple independent applications without re-entering credentials.

Example: A user logs into Curity via Client A (App A), and can then access Client B (App B) without logging in again.

  • Log in to Application A (Client A):
    • You’re redirected to Curity.
    • Curity asks for your username/password (or federates to LDAP/AD/Google).
    • After login, Curity creates a session and issues tokens for Client A.
  • Go to Application B (Client B):
    • Application B redirects you to Curity for login.
    • Curity detects an active session and issues tokens automatically — no credentials needed again.
  • Do you need to log in again?
    • No — if your Curity session is still active.
    • Yes — if your session expired, or if App B uses a different authentication profile/domain.

SSO in Curity

An SSO session (authenticated session) is created on the Identity Server after a successful authentication.

It contains information such as:

  • How the user authenticated (which authenticator)
  • When the user authenticated
  • Details about the authenticated user

When a new authentication request arrives, Curity checks whether an existing SSO session satisfies the requirements of that request.

The Identity Server may verify:

  • Is there an SSO session for the requested authenticator?
  • Is the session still valid (not expired or violating max_age)?
  • Did the client allow SSO to be used?

Only Curity can read the SSO session. It uses this session to construct the token returned to the client as proof of authentication. In OpenID Connect, that proof is the ID Token.

How SSO Works in Your Setup

You have multiple applications in the same cluster:

  • User Management → uses user-management-client
  • Portals → uses portals-client

Both clients use the same end-user authenticator, which delegates authentication to Entra ID (Azure AD) using OIDC.

Important: SSO happens at the Identity Provider (Curity), not in your applications.

If Curity already authenticated the user, and another app redirects the user to Curity:

  • Curity detects an existing login session (via session cookie).
  • Curity immediately issues tokens.
  • No login screen is shown again.

Requirements for SSO to Work

  • ✔ Both clients use the same authenticator.
  • ✔ They belong to the same Curity session domain.
  • ✔ SSO is enabled in System → Sessions.
  • ✔ Clients do NOT force re-authentication:
    • Do NOT send prompt=login
    • Do NOT set max_age greater than 0

SSO Flow Example

User logs into App A (User Management):

  • User Management redirects to Curity.
  • Curity redirects to Entra ID.
  • User signs in.
  • Curity creates an SSO session cookie under the Curity domain.
  • Tokens are issued to User Management.

User then opens App B (Portals):

  • Portals redirects to Curity for authentication.
  • The browser automatically sends the existing Curity session cookie.
  • Curity detects the active SSO session.
  • Curity immediately issues tokens (no Entra login).
  • User is logged in via SSO.

💡 Key Insight: The browser stores the session cookie for the Curity domain. Any application that redirects the user to that same Curity domain can benefit from SSO.

RBAC – Role-Based Access Control

Access is based on roles assigned to users.

  • Example:
    • User: Alice
    • Role: Admin
    • Permissions: Create, Update, Delete users
    • ✅ Alice can delete a user because her role allows it.
  • Used in: Curity, Keycloak

ReBAC – Relationship-Based Access Control

Access is based on relationships between entities (users, resources, groups, etc.), not just roles.

  • Example:
    • Alice owns Project A
    • Bob is a collaborator on Project A
    • Charlie is a manager of Alice
    • ✅ Bob can edit Project A (because of "collaborator" relationship)
    • ✅ Charlie can view Project A (because "manager of Alice")
    • ❌ Others can’t access Project A
  • Used in: SpiceDB, AuthZed

Tenant-Scoped Operations in User Management (UM)

The following operations in UM are all tenant-scoped:

  • Request handling
  • JWT validation
  • Mongo queries

Tenant Identification & Filtering

  • The Tenant document _id is the tenant identifier.
  • Queries for the User collection always filter on state.tenantid first.
  • The List Groups API filters use state.foreigngroup.tenantid.
  • The ScimSource aggregate carries TenantId and ties provisioning to that tenant when creating users/groups.

How Tenant ID is Propagated

  • K8s API → sends tenant ID as the x-tenant-id header.
  • REST APIs → send tenant ID as a claim in the Curity token.
  • gRPC FindTenantByHost from auth-gateway to user-management → only attaches a Bearer token; it does not pass the x-tenant-id header.
  • Permission checks → forward the x-tenant-id header on outgoing gRPC AuthZ calls.

SCIM URLs

  • SCIM URLs are tenant-scoped — they contain the SCIM source ID in the URL.

Curity profiles are created from Access Studio when:

LecTenantStatusActive
  AND !TenantStatusCurityConfigurationFailed
  AND !TenantStatusDeprovisioning
  AND !TenantStatusDeleted

    environment.Tenant.Capabilities.UserManagement
    OR Details.ResidencyOption == ResidencyOptionRemote
  )

!tenant.DomainName.None() && tenant.Capabilities.UserManagement
